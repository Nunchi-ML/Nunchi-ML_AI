# 해가 정면에 낮게 있던 도로 사진 찾기 (모델 ② 데이터 · G 확인용)

GLARE(미국 블랙박스 2,157장)에는 **찍은 시각 · 위치가 없어서** 해 높이와 방향을 알 수 없어요.
촬영 시각 · GPS · 카메라 방향이 함께 있는 사진을 찾아, 계산한 해 위치로 "해가 정면에 낮게 있던" 장면을 고릅니다.

| 쓰임 | 내용 |
|---|---|
| 모델 ② | 한국 도로 사진으로 학습 · 검증 사진 늘리기 (2인 라벨) |
| 모델 ③ G 확인 | 해 높이 · 방향 차이 Δ 와 실제 눈부심 단계의 관계 → 재혁님 공식 G 가 맞는지 |

### 한국 사진 넣어 재학습 (`retrain_korea.py`, 촬영 단위 GroupKFold)

| 시험 \ 학습 (macro F1) | GLARE 만 | 한국 만 | GLARE+한국 |
|---|---|---|---|
| 블랙박스 여행 175장 | 0.32 | 0.20 | 0.31 |
| 도로 광각 109장 | 0.28 | 0.40 | 0.31 |
| GLARE 130장 | 0.44 | — | 0.45 |

→ **한국 사진을 넣어도 거의 안 나아짐.** 원인 가리기:
- ① 화면 비율: 16:9 로 잘라 넣어도 0.27~0.32 → 원인 아님
- ② 해 위치(높이 · Δ) 특징 추가: 도로 광각 0.40 → 0.47 조금 나음, 블랙박스는 그대로
- ③ 블랙박스 여행 **안에서만** 학습 · 시험하면 0.52 (심함 재현율 0.67) — 화면 특징 · 해 위치 모두 같은 카메라 안에서는 신호가 있음

**결론: 특징이 아니라 카메라가 다양하지 않은 게 문제.** 한 번도 학습에 없던 카메라(블랙박스 여행이 시험에 들어가면 학습엔 고프로뿐)는 못 맞힘.
앱의 실제 입력은 **차 안 거치대의 폰 카메라** → 2019 iPhone 블랙박스가 제품과 가장 비슷한 데이터인데 한 번 뿐.
→ 직접 촬영은 하지 않기로 함 (PM 결정 2026-11-02). 카메라를 늘리려면 Mapillary 에서 달구벌대로 밖(대구 전역 · 다른 도시)의 차 안 촬영 묶음을 더 찾는 쪽.

참고 — **GLARE 0.57 vs 0.44 원인 (해결)**: 라벨 · 특징 파일은 번들 meta 의 sha256 과 똑같음. 차이는 **scikit-learn 버전**
(1.8.0 = 번들 · BE, 1.9.1 = AI venv) 에 따라 `GroupKFold` 가 영상을 폴드에 나누는 방식이 달라서. 같은 데이터 · 모델이 1.8 분할로 0.571, 1.9 분할로 0.444.
영상 33개뿐이라 분할 운이 큼 → 분할 30번 반복 시 **macro F1 0.52 ± 0.05 (0.41~0.62) · 심한 눈부심 재현율 0.32 ± 0.10** (번들 기록 0.52 는 운 좋은 분할).
`pilot_eval.repeated_cross_val` 추가 — 앞으로 점수는 반복 평균으로 보고.

### 기법을 바꾸면? (데이터 문제인지 기법 문제인지 가리기)

같은 사진 414장(GLARE 130 + 한국 284) · 촬영 단위 GroupKFold(6), macro F1:

| 방법 | 블랙박스 | 도로 광각 | GLARE |
|---|---|---|---|
| 숫자 12개 + LightGBM (지금) | 0.31 | 0.31 | 0.44 |
| 숫자 12개 + 로지스틱 / 랜덤포레스트 | 0.33 / 0.33 | 0.27 / 0.17 | 0.41 / 0.43 |
| 숫자 12개 카메라별 표준화 + 로지스틱 | 0.41 | 0.21 | 0.34 |
| **CLIP 사진 특징 + 로지스틱** (`clip_probe.py`) | 0.26 | 0.24 | 0.41 |
| CLIP 글 설명 비교 (학습 없음) | 0.19 | 0.49 | 0.29 (심함 재현율 0) |

→ 모델을 바꾸거나 특징을 사전학습 이미지 모델(CLIP)로 바꿔도 **처음 보는 카메라에선 0.2~0.4** 그대로.
**병목은 데이터** — 카메라 · 촬영 종류가 적음(학습에 쓸 수 있는 촬영 묶음이 GLARE 33 + 한국 13), 심한 눈부심 사진이 대부분 한 블랙박스 여행에 몰림.
(CLIP 은 PyTorch 가 커서 `.venv-clip` 별도 venv — 실행법은 스크립트 맨 위)

### 카메라 정보로 추정 — 화각 반영 해 위치 (`fov_probe.py`)

카메라 노출값(셔터 · ISO · EV)은 Mapillary 원본에서도 지워져 있어(EXIF 3개만) **지금 데이터로는 검증 불가** → 앱이 직접 찍을 때 기록해야 생김.
대신 Mapillary 가 주는 **초점거리 → 가로 화각** (블랙박스 53~66° · 도로 광각 70~108°) 으로 "해가 이 카메라 화면 어디쯤 있나" (u · v · r · in_fov) 를 계산해 넣음.
한국 284장, 촬영 단위 GroupKFold(5) — 블랙박스 여행이 시험일 때 학습엔 도로 광각뿐:

| 특징 | 블랙박스 macro F1 | 심함 재현율 | 눈부심 여부 | 도로 광각 macro F1 | 눈부심 여부 |
|---|---|---|---|---|---|
| 화면 12개 (지금) | 0.20 | 0.00 | 0.46 | 0.40 | 0.65 |
| 해 위치 (높이 · Δ) | 0.18 | 0.00 | 0.27 | 0.26 | 0.46 |
| **화각 반영 해 위치** | **0.34** | **0.62** | **0.75** | 0.13 | 0.32 |
| **화면 12 + 화각 반영** | 0.30 | 0.58 | **0.75** | **0.42** | **0.67** |

→ **처음으로 다른 카메라로 넘어가는 신호.** 같은 Δ 라도 화각이 다르면 해가 화면에 있느냐가 달라지는데, 이를 맞춰 주니 고프로로만 배운 모델이 블랙박스의 심한 눈부심을 0 → 62% 잡음.
도로 광각에서 해 위치만으론 약한 건 그쪽 라벨이 날씨(흐림) 영향을 크게 받아서 — 화면 특징과 같이 쓰면 둘 다 가장 좋음.
→ 앱 설계: 화면 특징 + **폰 GPS · 나침반 · 시각 · 카메라 화각** 으로 계산한 해 화면 위치를 같이 넣는 모델 ② v2 후보. (구름은 화면 특징이 담당)

### 모델 ② v2 후보 — GLARE 까지 한 모델로 (`v2_candidate.py`)

GLARE 는 촬영 정보가 없어 해 위치 칸을 빈칸으로 두고 GLARE + 한국 414장을 한 모델로 (촬영 단위 GroupKFold(6)):

| | 블랙박스 F1 · 심함 재현율 · 눈부심 여부 | 도로 광각 F1 · 눈부심 여부 | GLARE F1 · 눈부심 여부 |
|---|---|---|---|
| v1 화면 12 | 0.31 · 0.12 · 0.62 | 0.31 · 0.49 | 0.44 · 0.72 |
| v2 화면 12 + 해 위치 | 0.29 · 0.14 · **0.79** | 0.31 · 0.48 | 0.46 · 0.75 |
| v2 에 해 위치 빈칸으로 넣음 | 0.29 · 0.15 · 0.54 | 0.23 · 0.39 | 0.46 · 0.75 |

- 해 위치를 넣으면 **눈부심 여부(0 vs 1+)** 는 블랙박스에서 0.62 → 0.79 로 확실히 나음
- 하지만 GLARE 를 섞으면 **심한 눈부심**을 잡는 힘이 약해짐 (한국만 학습 0.62 → 섞으면 0.14). GLARE 130장이 해 위치 없이 '심함' 을 화면 특징으로만 가르쳐서 해 위치 신호가 묻힘
- 시각 · GPS · 방향은 날것으로 넣지 않고 **해 위치로 바꿔** 넣음 (날것은 장소 · 날짜를 외움). 아직 안 쓴 건 시각 · GPS 로 붙일 수 있는 **구름양(ASOS)**

→ v2 는 "눈부심 여부" 는 GLARE 와 섞어도 좋고, "심함" 까지 노리려면 해 위치가 있는 한국 데이터 위주로 학습해야 함.

### 날씨(구름양 · 일조) 붙이기 — ASOS 대구 143 (`fetch_asos.py` · `asos_probe.py`)

공공데이터포털 ASOS 시간자료 (`KMA_SERVICE_KEY`, `.env`) → 촬영 시각의 가장 가까운 정시 전운량(0~10) · 일조(0~1).

| 한국 라벨 284장 | 사진 | 눈부심(1 이상) | 해가 화면 안인 사진만 |
|---|---|---|---|
| 도로 광각 · 맑음(전운량 0~2) | 82 | 89% | 95% (61장) |
| 도로 광각 · 흐림(8~10) | 21 | **0%** | **0%** (10장) |
| 블랙박스 · 맑음 | 175 | 82% | 86% |

→ **"해는 정면인데 눈부심 0" 은 흐린 날** 이었음 (가설 확인). 흐리면 해가 화면 안이어도 눈부심 0.
블랙박스 여행은 하루 종일 맑음이라 날씨 차이를 볼 수 없음.

모델 (한국만, 촬영 단위 검증):

| 특징 | 블랙박스 F1 · 심함 · 여부 | 도로 광각 F1 · 여부 |
|---|---|---|
| 화면 12 + 해 위치 | 0.30 · 0.62 · 0.75 | 0.42 · 0.67 |
| 화면 12 + 해 위치 + **날씨** | 0.34 · 0.62 · 0.76 | **0.46 · 0.72** |
| 해 위치 + 날씨 (**화면 없이**) | **0.36 · 0.62 · 0.77** | 0.41 · 0.72 |

→ 날씨를 넣으면 둘 다 조금씩 나아짐. 그리고 **화면 없이 해 위치 + 날씨만으로도 화면 모델만큼** 맞힘
= 모델 ③ G (해 높이 · Δ · 구름) 를 화면 판단 없이도 쓸 수 있다는 근거. GLARE 와 섞은 v2 에선 날씨 효과가 묻힘 (도로 광각 F1 0.31 → 0.38 정도).

### 물리 특징 — 눈부심 각도 θ · CIE 식 본뜬 지수 · 시정 · 강수 (`physics_probe.py`)

θ = 시선과 해 사이 실제 각도 = arccos(cos 해높이 · cos Δ), 눈부심 지수 = 일사량 / θ² (CIE 불능 눈부심 식 형태). ASOS 에서 시정 · 강수도 받음.

| 특징 (한국만, 촬영 단위 검증) | 블랙박스 F1 · 심함 · 여부 | 도로 광각 F1 · 여부 |
|---|---|---|
| 해 위치(화각 반영) + 날씨 — 이전 최고 | **0.36 · 0.62** · 0.77 | 0.41 · 0.72 |
| θ + 눈부심 지수 (2개만) | 0.18 · 0.00 · 0.59 | 0.36 · 0.57 |
| θ + 지수 + 날씨 | 0.21 · 0.00 · 0.77 | 0.34 · 0.62 |
| 물리 전부 (+ 시정 · 강수 · 일사) | 0.28 · 0.04 · 0.77 | **0.49 · 0.77** |
| 화면 12 + 물리 전부 | 0.26 · 0.00 · 0.77 | 0.46 · 0.73 |

- **θ · 지수는 화각 반영 위치보다 못함.** 라벨이 '사람 눈' 이 아니라 '카메라 화면' 기준이라, 해가 화면 안이냐(화각에 따라 다름)가 더 중요. θ 는 운전자 눈 기준 G(모델 ③) 에 맞는 식
- 시정 · 강수까지 넣으면 도로 광각 눈부심 여부 0.72 → 0.77 로 나아지지만 블랙박스 심한 눈부심을 놓침 (촬영 묶음이 적어 특징을 늘리면 날씨에 끌려감)
- 순위 상관(눈부심 여부): 일조 +0.38 · 지수 +0.32 · 시정 −0.29 · θ −0.23 · 일사 +0.21 · 구름 −0.18 · 강수 −0.16
→ **지금 데이터 크기에선 '화각 반영 해 위치 + 구름 · 일조' (7개) 가 가장 균형 좋음.** 특징을 더 늘리는 건 촬영이 늘어난 뒤에.
